# Event envelope v2: the reader, the upcaster and held streams (F1a)

Status: implemented by F1a (goodqa#15372), which is PARTIAL against the F1 ticket. F1a reads every stored event through a v2 envelope view built by an upcaster, while the schema, the stored bytes and everything fabd writes stay exactly as they are. The migration (stored event ids, stored envelope bytes, a stored quarantine table with release, the writer switch) is F1b.

## What changed

- `internal/envelope` has the v2 view (`View`), `Upcast` (the view of a stored `events` row), `DecodeEvent` (the one decode function every event decode site uses; a source scan fails on a direct decode elsewhere) and `EventID`.
- `reducer.Replay` accepts only `[]envelope.View`. The outbox path joins `events` on `(mission_id, seq)`, so the consumer and replay paths build the same view from the same row.
- A mission with a stored event this build cannot decode is held instead of stopping fabd.

## The view of a v1 row (normative, frozen by the vectors)

| Field | Value |
|---|---|
| `schema_version` | 1 on stored rows, 2 on the view |
| `event_id` | `evt_` plus a ULID: time is floor of the epoch milliseconds of `at`; body is the first 80 bits of SHA-256 over `"fabric.v1.event_id"`, 0x00, u32be(len(mission)), mission, u64be(seq); upper-case Crockford; shape `^evt_[0-7][0-9A-HJKMNP-TV-Z]{25}$`. Never an ordering key (seq is). A mission that is empty, over 64 bytes or not ASCII is refused |
| `tenant_id` | `t_personal`, the personal tenant literal fixed here (ADR 0001 choice 3) |
| `principal` | `{issuer: "legacy-unverified", subject: events.actor}`. It never carries authority: operator checks keep reading the actor. A payload key named `issuer` or `principal` cannot change it |
| correlation, causation, trace and span ids | absent |
| `at` | UTC, six fractional digits, `Z` |
| optional fields | absent, never null |

Canonical bytes of the view are RFC 8785 over `{schema_version, event_id, tenant_id, principal, mission, seq, kind, at, payload}`. They are computed on demand and never on the replay or consumer paths; a canonicalisation failure is never a hold.

Vectors: `internal/envelope/testdata/vectors.json` (sha256 `9cef31cd9a5e2dd490583e54ce004ae24fb61154a2534d47f776edf88b4f508e`) is generated by `python3 -I tools/gen_vectors.py`, which shares no code with the Go implementation; `--check` fails if the committed file differs.

### A hand-worked vector

Mission `m_demo1`, seq 1, `at` = 2025-11-08T00:00:00.123456Z (1762646400123456 microseconds):

1. Time: 1762646400123456 microseconds is 1762646400123 whole milliseconds, which is `0x019a65e99c7b`, six bytes `01 9a 65 e9 9c 7b`.
2. Preimage: `"fabric.v1.event_id"` (`6661627269632e76312e6576656e745f6964`), `00`, the length 7 as four bytes (`00000007`), `m_demo1` (`6d5f64656d6f31`), seq 1 as eight bytes (`0000000000000001`). Together: `6661627269632e76312e6576656e745f696400000000076d5f64656d6f310000000000000001`.
3. SHA-256 of the preimage: `25061356ca0ad4700bfb4bb4f82a3ced3dd21ec53ae733ebc96cdd6d99504fb6`; its first 10 bytes are the body: `25061356ca0ad4700bfb`.
4. The 128 bits are the time then the body: `019a65e99c7b25061356ca0ad4700bfb`. Pad two zero bits in front (130 bits) and read 26 groups of five bits: `0 1 19 9 18 30 19 7 3 27 4 20 3 1 6 21 22 10 1 11 10 7 0 2 31 27`.
5. Crockford characters for those groups: `0 1 K 9 J Y K 7 3 V 4 M 3 1 6 N P A 1 B A 7 0 2 Z V`.
6. `event_id` = `evt_01K9JYK73V4M316NPA1BA702ZV`, the first vector in the file.

## Held streams

A held stream is a mission whose stored event this build cannot decode. It is a different thing from the in-memory `sched.park` map (a sweep step failed) and from the `MISSION_PARKED` event kind (a mission blocked after repeated pre-launch failures); neither is listed or counted as held.

**Decode failure, exactly:** a v1 `Event` decode error; a kind not in the registry (`domain.KnownEventKinds`); a typed payload that rejects a value (unknown keys never fail); a mismatch between the row and the payload on `kind`, `mission` or `seq`.

**The hold is data, not schema:** a row in the existing `outbox_cursors` table, consumer `sched.hold.<mission>`, so `deploy-live.sh` and the binary-only `deploy-rollback.sh` both apply.

- The `sched` cursor always advances. The main page is read, held rows are skipped and the cursor is acknowledged in one transaction that locks the cursor row (`FOR UPDATE`); each delivered row is applied in the same transaction, so a crash can only redeliver, never lose a row, and two schedulers never read the same page.
- On a decode failure the row's mission gets a hold row (`last_id` = the poison row's outbox id minus one) in the same transaction as the ack. Rows of a held mission on the main page are skipped.
- Each tick drains every hold row: it pages the mission's rows after `last_id` and up to the scheduler cursor, applies them in order, and stops at the first row that still cannot be decoded. The hold row is deleted, in a transaction that locks the cursor row, only when the drain has caught up with the cursor and the mission's whole log reads through the v2 reader. A hold found by a replay or by a start (the log failed to decode after START_ATTEMPT; the attempt is abandoned first, then the hold is written) is created at the current cursor, so rows already applied are never redelivered, and it stays until the log decodes.
- `consumeOutbox` counts only applied rows, so a tick over only held rows is idle (no hot loop).
- `Execute` refuses a command to a held mission with `ErrStreamHeld`, a plain sentinel that is never stored and never a `*store.Refusal`: nothing is written, and the same command id succeeds after the fix. The stored-command replay lookup runs first, so a command already stored still replays its first response. The abandon of an attempt is exempt from this check only; every other check on the command still runs, and the existing unknown-kind check still applies to it (a rare race with another binary that appends an unknown kind between the start and the abandon leaves the attempt non-terminal; see the runbook).
- Dispatch, `wakeExitedJobs`, `ExpireLeases` and the unknown-attempt sweep exclude held missions in SQL. A held mission keeps its slot and spend holds: it is capacity-safe (under-admission), and the gauge reports it.

**Visibility:** `fab streams held` lists held missions (mission, event kind name, reason class, time; never payload text) from the hold rows; `fab streams held --scan` is the only full decode of history and also finds missions not yet held. `fab status` prints `held streams: N`. The gauge `fabric_held_streams` is the number of distinct held missions (hold rows plus missions whose log holds a kind this build does not know), computed in SQL without decoding payloads.

**Alert rule (documented, not wired):** alert when a mission has been held for more than 10 minutes. Wiring it needs a time source that a drain does not touch (`outbox_cursors.updated_at` moves on every drain advance) and a new column would break the no-schema-change rule, so the wiring is a ticketed follow-up.

## Operator procedure for a held stream

1. `fab streams held` (and `--scan` before a deploy) shows which missions are held and the kind and reason class. Nothing else changes while a mission is held; the others keep flowing.
2. Fix forward: deploy a decoder that reads the row. The next drain applies the held rows in order and releases the hold.
3. If the data is wrong rather than the decoder: repair the stored row as the database owner, with the append-only trigger disabled for that one transaction and re-enabled in it, after a backup. Never use the application role for this.
4. A held mission with a non-terminal attempt blocks the `busy` gate of `deploy-live.sh` and `deploy-rollback.sh`: list such missions before a deploy (`fab streams held` with the attempts in `fab status`), and resolve them first.
5. Rollback then redeploy: the old binary has no hold check and can append to and deliver a held mission's rows during the rollback window. Do not delete `sched.hold.*` rows before the redeploy: the scheduler cursor has moved past rows of that mission that the old binary applied only in part, and deleting the hold would strand those rows. Keep the holds; the redeploy drain replays the mission's rows from the hold point in order and the final state is correct, but each row from the rollback window is delivered twice (an inflated `waits_resumed_total`, `waits.since` reset).

Disclosed limits: any application-role session can delete a hold row and release the hold with no audit trail (F1b's audited quarantine replaces it); the deploy snapshot check runs before fabd starts and does not allow for `outbox_cursors` changes; F1b must reproduce the `event_id` function and the field table exactly and migrate `sched.hold.*` rows into its quarantine table.
